# コード内コメントのルール

pre-commit (prek.toml) の `check-comment-refs` フックが機械チェックする。落ちたらここを読み直す。

## 何を書くか

- コメントは「なぜこのコードがあるのか」「どういう意図か」を説明する。コードの内容をなぞるだけの自明なコメントは書かない
- 実装中に見つけた非自明な挙動・落とし穴（ライブラリの既定動作、環境依存の制約、性能上の理由）は、その場所に理由を残す。なぜそうしているかが伝わらないコードは、後から削除・変更されて壊れる

## 自己完結させる（MUST）

コメントは **コード＋コメントだけで背景・判断基準・なぜこう書いたかが理解できる** ように書く。開発計画上の記号を単体で書くと、docs や PR を引かないと意味が取れなくなる。

フックが拒否するパターン:

- 計画記号・ID 単体（`AC-3` `M-8` `T-1` `B-4-2` `I-1` `F-01` `Step 4` `Phase 1` `Task 2` `Success Criteria`）
- 本文中の ADR 番号（`ADR-0006`）
- SPEC 直接参照（`SPEC § 5.5` `SPEC 記載の通り`）
- issue 番号 / PR 番号 / コミット SHA の単体参照
- 本文中の `docs/...` パス

## 許容される形

自己完結した説明を書いた **うえで**、末尾に追加ポインタを置くのは可。フックは「〜を参照 / 参考 / 詳細は / 経緯は / see」が付いていれば通す。

NG:

```rust
// AC-3: 削除済み行も返す
```

OK:

```rust
// 削除済みの行も list 結果に含める。UI 側で「削除済」バッジを出すために必要。
// 詳細は docs/specs/2026-08-16-f02-page-stamp-numbers-design.md を参照。
```
