# フェーズ3: アニメーション機能 設計書

## 背景と目的

フェーズ2までで、3枚の画像（`typing1` / `typing2` / `idle`）の登録と `animationSpeed` の保存はできている。しかしメインウィンドウは `idle` 画像を静止表示するだけで、キーボード入力を検知する仕組みがない。

フェーズ3では、他のアプリへの入力も含めたキーボード入力を検知し、それに応じてマスコットを動かす。完了時には「キーを打つとマスコットが2枚の画像を交互に表示し、打つのをやめるとアイドル画像に戻る」状態になる。

## スコープ判断（確定事項）

- 対象OSは **Windows・macOS・Linux(X11)** の3つ
- 画像の切り替えは**キー入力ごと**に行う（タイマーで自動的に交互表示する方式は採らない）
- アイドルに戻るまでの時間は**設定項目**にする（`idleTimeout`）
- キー検知には**イベントフック型のライブラリ**を使う。検知部分は差し替え可能な境界の裏に置く
- 表示フレームを決める状態管理は **Rust側に集約**する（OSに依存しない純粋関数にして `cargo test` で検証する）
- 検知部分から外に出すのは**「キーが押された」という事実だけ**。どのキーが押されたかは保持もログ出力もしない

### スコープ外

- フェードなどの切り替え効果（2枚の交互表示では即時切り替えの方が打鍵感に合うため、実装しない）
- macOSの入力監視権限をユーザーに案内する画面（`docs/tasks.md` の 4.2「キーフック権限エラーの処理」で扱う）
- 3枚を超えるフレームや複数のアニメーションパターン（フェーズ5）

## 全体構成とデータフロー

`docs/architecture.md` の3ゾーン分離に従い、`src-tauri/src/animation/` を新設する。

| ファイル | ゾーン | 役割 |
|---|---|---|
| `mod.rs` | — | 型定義。表示フレーム `Frame`（`Idle` / `Typing1` / `Typing2`）、動作設定 `AnimationConfig`、状態 `AnimationState` |
| `key_source.rs` | Input | キー検知ライブラリを包む境界。キー押下のたびにチャネルへ通知を送る。キーの種類は捨てる |
| `logic.rs` | Logic | 状態遷移の純粋関数。I/Oも時刻取得も行わない |
| `runner.rs` | Output | 常駐スレッド。通知を待ち、`logic.rs` を呼び、フレームが変わったときだけイベントを送る |

データの流れ:

1. `key_source` がOSからキー押下を受け取り、チャネルに通知を流す
2. `runner` がチャネルを待つ。待ち時間の上限は「アイドルに戻るまでの残り時間」とする。これにより、キー通知とアイドル復帰を1つのスレッドで扱え、待機中のポーリングが不要になる
3. フレームが変わったら、イベント `animation-frame`（ペイロード: `"idle"` / `"typing1"` / `"typing2"`）をメインウィンドウへ送る
4. メインウィンドウはイベントを受けて、表示する画像を差し替える

メインウィンドウは設定の適用時に3枚の画像をすべて読み込んで保持する。フレームの切り替えでは保持済みの画像を差し替えるだけにし、フレームごとの画像読み込みを発生させない。

## 動作ルール（状態遷移）

状態は「現在のフレーム」「最後にフレームを切り替えた時刻」「最後にキーが押された時刻」の3つを持つ。初期状態は `Idle`。

### キーが押されたとき

- 現在が `Idle` なら、すぐに `Typing1` へ切り替える
- 現在が `Typing1` / `Typing2` なら、最後の切り替えから `animationSpeed` 以上経っている場合だけ、もう一方のtypingフレームへ切り替える。経っていなければフレームは変えない
- いずれの場合も「最後にキーが押された時刻」を更新する

### 時間が経過したとき

- 現在が `Typing1` / `Typing2` で、最後のキー押下から `idleTimeout` 以上経っていたら `Idle` へ戻す

### その他の扱い

- キーの押しっぱなし: OSの自動リピートも入力として扱う。押している間は `animationSpeed` の間隔で動き続ける
- キーを離したとき: 何もしない
- このアプリ自身への入力: 設定ウィンドウでの入力にも反応する（グローバル検知なので区別しない）

### `logic.rs` の関数

- `on_key(state, now, config) -> AnimationState`: キー押下時の遷移
- `on_timeout(state, now, config) -> AnimationState`: 時間経過時の遷移
- `next_wait(state, now, config) -> Option<Duration>`: 次にアイドル復帰を判定するまでの待ち時間。`Idle` のときは `None`（キー通知だけを待つ）

時刻はすべて引数で受け取る。

## 設定

### 項目の追加

`Settings` に `idleTimeout`（ミリ秒）を追加する。Rust側の構造体と `src/types/settings.ts` の両方を変更し、同期を保つ。

| 項目 | デフォルト | 範囲 |
|---|---|---|
| `animationSpeed`（既存） | 200ms | 50〜500ms |
| `idleTimeout`（新規） | 1000ms | 300〜5000ms |

- 既存の `settings.json` との互換性は考慮しない（開発中のため、後方互換やデータ移行は行わない）
- `sanitizeSettings` に `idleTimeout` を加える
- 設定ウィンドウには、Animation Speed の下にスライダーを1つ追加する

### 範囲外の値の扱い

現状、範囲を制限しているのは設定ウィンドウのスライダーだけで、バックエンドは範囲外の値を拒否しない。`settings.json` を手で編集すれば 0ms のような値が入りうる。

フェーズ3では保存時の拒否は追加しない。代わりに、`Settings` から `AnimationConfig` を作る純粋関数で両方の値を上の範囲に丸める。これにより、どんな値が保存されていても `runner` が異常な間隔で動くことはない。

### 設定変更の反映

`runner` が参照する `AnimationConfig` は共有状態として持つ。`save_settings` と `reset_settings` が成功したときに更新するので、再起動なしで速度と復帰時間の変更が反映される。

## フロントエンド

- `src/constants.ts` にイベント名 `ANIMATION_FRAME_EVENT`（`"animation-frame"`）を追加する
- `src/animation.ts`（新規）に、フレーム名と読み込み済みの3枚の画像から表示する画像を決める純粋関数を置く
  - typing画像が未登録なら、そのフレームでは `idle` 画像を表示する
  - `idle` 画像も未登録なら `null` を返し、現在と同じプレースホルダーを表示する
- `src/App.vue` は次の2点を変更する
  - `applySettings` で3枚の画像をすべて読み込んで保持する
  - `animation-frame` を購読し、現在のフレームを更新する

## OS別の制約とエラー処理

| 環境 | 挙動 |
|---|---|
| Windows | 追加の権限なしで動く |
| macOS | 入力監視の権限が必要。許可がない間は検知できず、`idle` 表示のまま動く |
| Linux(X11) | 動く |
| Linux(Wayland) | 他アプリへの入力は原理的に取得できない。XWayland経由で動いているアプリへの入力だけに反応する可能性がある |
| WSLg（開発環境） | WSLg上のウィンドウへの入力だけに反応する。Windows側のアプリへの入力は見えない |

- 起動時は環境を判定せず、常に検知の開始を試みる。失敗したら警告ログを出し、`idle` 表示のままアプリを続行する
- 実行中に検知スレッドがエラーで止まった場合も同じ扱いにする。エラーログを出して `idle` 表示に留め、自動での再試行はしない
- WaylandとWSLgの制約は README に書き足す

## ライブラリの選定

イベントフック型のライブラリの候補は `rdev` とその派生版である。macOSでは、Tauriと併用したときにクラッシュする問題が報告されており、派生版を選ぶ必要がある可能性がある。

実装の最初のタスクで次を行う。

1. 候補のライブラリを比較し、3つのOSへの対応状況とメンテナンス状況を確認する
2. 開発環境（WSLg）で、WSLg上のウィンドウへの入力を検知できることを確認する
3. 結果をこの設計書の本節に追記する

3つのOSで動くイベントフック型のライブラリが見つからない場合は実装を止め、ポーリング型のライブラリ（`device_query`）への切り替えを相談する。検知部分は `key_source.rs` の関数1つに閉じているので、切り替えてもほかのモジュールは変わらない。差し替えのための抽象（トレイトなど）は作らない。

### 選定結果

- 採用: `rdev`（git依存、https://github.com/Narsil/rdev のコミット `c77b4e5456301cfa7f2226020f2a58f2f8d77c5d`、Cargo.tomlのバージョン表記は 0.6.0）。Linuxでは `x11` featureを有効にする
- 理由:
  - crates.io の最新版 `rdev` 0.5.3（2023-06-26公開）には、macOSでメインスレッド以外から `listen` を呼ぶと落ちる問題の修正が入っていない。0.5.3のソースに `is_main_thread` は存在しない（crateを取得して確認）
  - 修正は PR #147 「MacOS: set_is_main_thread」（2025-05-20 マージ）で、`rdev::set_is_main_thread(false)` を `listen` の前に呼ぶ形で提供される。Issue #165 で、報告者が指定コミットの git 依存で解消したと報告している。Issue #165 は修正が crates.io に未公開のまま open
  - 派生版は調べていない。本家のコミットで基準を満たすため不要と判断した
  - 上記コミットは Issue #165 の報告者が動作を確認したもの。本家 main にはその後の変更（objc2 への移行など）があるが、未検証のため追従しない
- 未確認:
  - Windows と macOS での実機動作（開発環境がWSLgのため）。macOSの修正は第三者の報告に基づく
  - macOSでは `set_is_main_thread(false)` 後、キー名の解決がメインキュー経由になる。メインスレッドのイベントループが動いている前提であり、Tauriアプリでは満たされる想定だが実機では未確認
  - macOSでの入力監視の権限が必要。無い場合は `listen` がエラーを返し、マスコットはidleのままになる

## テスト

### 層2: Rust純粋関数（最も厚くする）

`logic.rs` を、時刻を引数で渡して検証する。実際に時間を待つテストは書かない。

- `Idle` でキーが押されたら `Typing1` になる
- 最低表示時間内のキー押下ではフレームが変わらず、「最後にキーが押された時刻」だけが更新される
- 最低表示時間を過ぎたキー押下で `Typing1` と `Typing2` が交互に切り替わる
- 最後のキー押下から `idleTimeout` が過ぎると `Idle` に戻る。過ぎる前は戻らない
- `next_wait` が `Idle` で `None`、typing中は残り時間を返す
- `AnimationConfig` を作る関数が範囲外の値を丸める

設定については、`idleTimeout` のデフォルト値を検証する。

### `runner`

キー通知のチャネルとイベントを送る関数を引数で受け取る形にする。OSのフックもTauriも使わずに、通知を流すと期待した順でフレームが送られることを検証する。

### 層1: Vitest

- フレーム名から表示する画像を決める関数（未登録時の代替を含む）
- `sanitizeSettings` が `idleTimeout` を扱うこと
- 設定ウィンドウの Idle Timeout スライダー

### 手動確認（`key_source`）

OSのフックに依存するため自動テストの対象外とする。動かせる環境で次を確認する。

1. このアプリ以外のウィンドウでキーを打つと、マスコットが2枚の画像を交互に表示する
2. 打つのをやめると、`idleTimeout` の経過後に `idle` 画像へ戻る
3. キーを押しっぱなしにすると、`animationSpeed` の間隔で動き続ける
4. 設定ウィンドウで `animationSpeed` と `idleTimeout` を変えて保存すると、再起動なしで反映される
5. typing画像を未登録にすると、入力中も `idle` 画像が表示される
